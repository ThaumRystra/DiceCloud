# Fix the build before chasing upgrades

The most valuable improvements to the Reverent Abyss fork before it moves to Oracle's ARM VPS are operational, not architectural. **The current Dockerfile clones upstream ThaumRystra/DiceCloud instead of building the fork, so not one 2d10 change would ship.** It also builds only for x86_64, floats MongoDB on `mongo:latest` (now 8.x), keeps uploaded files and archived characters inside the container where a rebuild deletes them, and runs with default `meteor/meteor` database credentials and open public signup. Every one of these is cheap to fix, has a proven fix in a fork or upstream branch, and touches none of the engine files the 2d10 work changed. The big modernisation, Meteor 3 plus Vue 3, is real and eventually unavoidable: Meteor 2.x reached end of life in December 2025 and its Node 14 runtime in April 2023. But it is a multi-month re-port, and upstream's own attempt (branch `DC-16`) edits 12 of the fork's modified files and has sat unfinished since May 2026. One assumption controls the whole plan and has not been tested: **that a Meteor 2.16 server bundle built on x86 will run on ARM64 after its native modules (fibers, bcrypt) are rebuilt there.** Meteor never shipped Linux ARM support for 2.x, and no fork has published a working native aarch64 image. So the first job is a one-evening proof of concept on the A1 instance. If it fails, the platform migration stops being optional and moves to the front of the queue.

## Seven cheap fixes decide whether the move works at all

**Change 1, building the fork's own source**, is the precondition for everything else. The fork's Dockerfile runs `git clone https://github.com/ThaumRystra/DiceCloud`, installs Node 14 through NodeSource's deprecated `setup_14.x` script, and builds with `--architecture os.linux.x86_64` (local: `Dockerfile`). Several forks have already fixed exactly this by copying `app/` into the build. faultoverload's `Dockerfile.production` is the cleanest drop-in: two new files, a non-root build user because "Meteor refuses to install as root", a `--server-only` build, and a `node:14-bullseye-slim` runtime chosen to avoid "the EOL Buster repo failures" ([faultoverload compare](https://api.github.com/repos/ThaumRystra/DiceCloud/compare/develop...faultoverload:develop)). Its catch is that it pins Meteor 2.12 while the fork runs 2.16, so the pin must be bumped. Arbel-arad's build is a warning sign rather than a template, because it runs a **Node 15** runtime against Meteor 2.16's Node 14 ([Arbel-arad Dockerfile](https://raw.githubusercontent.com/Arbel-arad/DiceCloud/develop/Dockerfile)). The Meteor guide is blunt on this point: "If you use a mis-matched version of Node when deploying your application, you will encounter errors!" ([Meteor Guide: Deployment](https://guide.meteor.com/deployment.html)). Upstream PR #394 does a similar 1-file rework on Debian 12. PR #389 also works but rewrites `package-lock.json`, so take its ideas rather than its lockfile ([PR #394](https://github.com/ThaumRystra/DiceCloud/pull/394)). The effort is hours, the conflict with RA is zero, and the verdict is unconditional.

**Change 2, the ARM64 path**, is where the project carries real technical risk. A Meteor maintainer stated in April 2025 that 2.x ARM support was Mac-only, that "Linux ARM support arrived in Meteor 3.x", and that Meteor's pipelines no longer build ARM for 2.x ([Meteor forums](https://forums.meteor.com/t/release-2-16-1-beta-0-is-intel-only-can-arm64-be-added/63405)). The workaround follows from the fact that a server bundle is mostly plain JavaScript: build it on x86, copy it into an arm64 Node 14 image, and run `npm install` in `programs/server` there, so `fibers`, `bcrypt` and `sharp` compile or download arm64 binaries. hafadei's fork contains a GitHub Actions workflow built for exactly this "cross-arch ARM deployment", but it does not show the rebuild step on the target ([hafadei compare](https://api.github.com/repos/ThaumRystra/DiceCloud/compare/develop...hafadei:develop)). faerysteel's fork removes a second blocker. The Vuetify loader depends on node-sass 4.14.1, which "publishes no darwin-arm64 binary for Node 14", so faerysteel vendors the loader as a local package that uses dart-sass instead ([faerysteel compare](https://api.github.com/repos/ThaumRystra/DiceCloud/compare/develop...faerysteel:develop)). That fix matters only if you ever build *on* ARM. A build in x86 CI sidesteps it. The fallbacks are poor. x86 emulation under QEMU is slow. Oracle's AMD Always Free micro instance has only 1 GB of RAM, and one upstream self-hoster reported that `meteor run` struggled until 8 GB ([Issue #398](https://github.com/ThaumRystra/DiceCloud/issues/398)). If the proof of concept fails, the realistic answer is to host on x86 elsewhere or bring the Meteor 3 migration forward.

**Change 3, pinning MongoDB 7.0 as a single-node replica set**, fixes a latent break and a performance gap at once. Meteor 2.16 ships Node driver 4.17.2, which fully supports MongoDB 7.0 but only partially supports 8.0 ([MongoDB driver compatibility](https://mongodb.com/docs/drivers/node/v5.6/compatibility)). Meteor staff's compatibility table for 2.10 through 3.0-beta lists 7.0 as the newest compatible server ([Meteor forums](https://forums.meteor.com/t/mongodb-6-0-end-of-life-on-july-31-2025-automatic-atlas-cluster-upgrades-to-8-0/63752)). `mongo:latest` in the fork's compose file now resolves to 8.x, so any fresh pull could land on an unsupported major version. That may explain the MongoDB start failures in upstream issue #398, though the link is unproven. Upstream's own DC-16 branch pins `mongo:7` and adds `authSource=admin`, a two-line change you can port by hand ([DC-16 compose](https://github.com/ThaumRystra/DiceCloud/blob/DC-16-migrate-to-meteor-3/docker-compose.yml)). MongoDB 7.0 is supported until **31 August 2027** ([MongoDB lifecycles](https://www.mongodb.com/products/updates/longer-lifecycles-for-mongodb-7-0-and-8-0/)). The research also found that the fork **does not actually run redis-oplog**. The package is missing from `.meteor/packages`, and the calls `startCaching?.()` and `disableRedis?.()` are optional-chained, so they silently do nothing (local: `imports/server/config/redisCaching.js`). With no `MONGO_OPLOG_URL`, Meteor falls back to polling for reactivity. A single-member replica set (`--replSet rs0`, a one-time `rs.initiate`, `MONGO_OPLOG_URL=mongodb://.../local`) restores oplog tailing. JPugetGil's production kit does this with a keyFile ([JPugetGil compose](https://raw.githubusercontent.com/JPugetGil/DiceCloud/develop/deploy/compose.yml)). The friction is that a replica set with authentication needs a keyFile even for one node, and the `rs.initiate` hostname must match the compose service name.

**Change 4, persisting file storage**, prevents a quiet disaster. When S3 is not configured, uploads go to relative paths inside the bundle (`assets/app/userImages`, `assets/app/archiveCreatures`), and only Mongo has a volume mount. Worse, `archiveCreatureToFile` **deletes the creature from MongoDB after writing the archive file** (local: `imports/api/creature/archive/methods/archiveCreatureToFile.js`). A player who archives a character and then sits through a container rebuild loses that character for good. Either mount volumes at those paths (confirm the resolved path by uploading an image and searching the container) or point S3 settings at OCI Object Storage, which gives 20 GB free ([Oracle Always Free Resources](https://docs.oracle.com/en-us/iaas/Content/FreeTier/resourceref.htm)). Two details of the S3 route are unverified: the client hardcodes `region: 'ENAM'`, which may need changing for OCI's SigV4 signing, and OCI's S3-compatible endpoint needs Customer Secret Keys and path-style URLs.

**Change 5, reliability**, matters more on Oracle than elsewhere, because Oracle can reclaim the instance. Nothing exists today: no backup, no `restart:` policy, no log rotation (local: `docker-compose.yml`). The kit is a nightly `mongodump --archive --gzip` copied to Object Storage **and** somewhere outside Oracle, a backup of the file-storage volume, `restart: unless-stopped`, a Mongo healthcheck gating app start, json-file log caps, and an uptime monitor running off the box against the existing `/api/status` endpoint. Oracle's five free volume backups are a useful second layer, but they are only crash-consistent.

**Change 6, the security baseline**, addresses configuration exposure rather than code bugs. The compose file uses `meteor/meteor` as Mongo root credentials and publishes port 3000 on all interfaces over plain HTTP. No `Accounts.config`, `forbidClientAccountCreation` or `validateNewUser` exists anywhere, so anyone who finds the URL can register (local: `imports/api/users/Users.js`, `client/ui/pages/Register.vue`). Meteor's own options cover this in a few lines: `forbidClientAccountCreation` rejects client `createUser` calls, and `Accounts.validateNewUser` can enforce an allowlist from private settings ([Meteor v2 Accounts docs](https://v2-docs.meteor.com/api/accounts-multi.html)). Reusing the existing `Invites` collection is harder, because it is tied to Patreon tiers. Put Caddy in front for automatic HTTPS and WebSocket proxying, set `HTTP_FORWARDED_COUNT=1` so rate limits see real client IPs, create a least-privilege Mongo app user, and hide the Google and Patreon buttons, which fail without service configuration. The Meteor security guide says that "every production Meteor app that handles user data should run with SSL" ([Meteor Guide: Security](https://guide.meteor.com/security.html)). Add HSTS and similar headers first, and leave a strict CSP for later, because Vuetify's inline styles break under `default-src 'self'`.

**Change 7, de-hardcoding `dicecloud.com`**, is a handful of one-line edits. Invite links are built as `https://dicecloud.com/invite/${token}` (`InviteDialog.vue:79`). Email comes from `no-reply@dicecloud.com` (`accountsEmailConfig.js:3`). Email logos and printed-sheet link bases also point upstream. `Meteor.absoluteUrl()` plus a `MAIL_FROM` setting, which is the pattern JPugetGil adopted ([JPugetGil README](https://raw.githubusercontent.com/JPugetGil/DiceCloud/develop/README.md)), fixes all of them. For email itself, Oracle blocks outbound port 25 but includes 3,000 free Email Delivery messages a month ([Oracle Always Free Resources](https://docs.oracle.com/en-us/iaas/Content/FreeTier/resourceref.htm)). Without `MAIL_URL`, Meteor prints emails to stdout and keeps working ([Meteor Email docs](https://docs.meteor.com/api/email.html)), which is an acceptable fallback for a small group. Remove the placeholder `MAIL_URL=smtp://EMAIL:PASSWORD@SERVER:PORT`, though: an invalid host probably throws errors rather than falling back (unverified).

## The dice engine is where improvements and 2d10 collide

Most improvements avoid the RA code entirely. Two candidates land directly on it, and they deserve the most care.

**Change 9, auditing the roll path**, comes from JPugetGil's fork, the only large maintained derivative (87 commits ahead, active as of 19 October 2026). Its October 2026 security commits fix "action results never come from the client" and a bug where the client "knew the dice seed before the roll" ([JPugetGil compare](https://api.github.com/repos/ThaumRystra/DiceCloud/compare/develop...JPugetGil:develop)). The fork's own investigation explains why this probably applies to Reverent Abyss too. Dice come from `Alea(actionId)`, a seeded PRNG designed so that "the client simulation and the server replay produce identical rolls" (local: `DICE_INVESTIGATION.md`, `getDeterministicDiceRoller.ts`). A client that knows the action ID before rolling can, in principle, predict or reroll its 2d10 results. That matters less among trusted friends than on a public site, but a GM using this for a homebrew system should know it. The fix touches exactly the code `rollCoreDice` sits on, so conflict risk is high. The research team read only JPugetGil's commit titles, not the diffs, and JPugetGil is on Meteor 3, so its code cannot be cherry-picked. Treat this as a design review followed by a careful re-implementation, with RA's dice tests as the safety net. The verdict is to do it in the first weeks after launch, not before.

**Change 11, small upstream cherry-picks**, is mostly safe. PR #403 is a one-character typo fix with no overlap. Branch DC-6 fixes creatures summoned from libraries arriving with no properties, in seven files the fork never touched, though it is still marked "Began testing" ([DC-6 branch](https://github.com/ThaumRystra/DiceCloud/tree/DC-6-creatures-summoned-from-libraries-have-no-properties)). PR #401 fixes a `bassiveBonus` typo in `computeVariableAsSkill.js`, but the fork already deleted the 5e passive-advantage block in that file, so it is probably moot ([PR #401](https://github.com/ThaumRystra/DiceCloud/pull/401)). PR #400 adds a `minValue()` dice function to `parser/functions.ts` ([PR #400](https://github.com/ThaumRystra/DiceCloud/pull/400)). It could be useful for homebrew, but the fork's investigation found that `reroll()` and `explode()` in that same file bypass the deterministic InputProvider. Check which RNG path #400 uses before merging, or it will roll differently on client and server. PR #387 (library desync) no longer merges cleanly and may already be covered by upstream commit d42d2a72. PR #347 (generic webhooks) is stale but isolated. PR #353 (dddice 3D dice) and PR #333 (flat damage reduction) both hit the dice or damage pipeline at pre-refactor paths and are not worth the conflict. The upstream maintainer has merged only one community PR since November 2024 ([upstream closed PRs](https://api.github.com/repos/ThaumRystra/DiceCloud/pulls?state=closed)), so the fork has to cherry-pick from PR heads itself instead of waiting.

No fork changes the core d20 roll or replaces the 5e rules engine, so Reverent Abyss appears to be unique. The closest prior art, PR #399's optional `gameSystem` field, was closed unmerged without a signed CLA ([PR #399](https://github.com/ThaumRystra/DiceCloud/pull/399)). There is no rules-plugin pattern to borrow. The fork's approach of keeping RA logic in new `RA_*.ts` files and one shared roller is already the most modular design observed, and it will survive a future re-port best.

## Library seeding and dependency patching pay off after launch

**Change 10, library export and import**, solves the problem every self-hoster hits: a fresh instance is empty. Upstream issue #398 complains that the example settings produce "an empty instance" ([Issue #398](https://github.com/ThaumRystra/DiceCloud/issues/398)), and the maintainer closed the instance-export request #99 with character archives only, not libraries ([Issue #99](https://github.com/ThaumRystra/DiceCloud/issues/99)). ardunaline's fork adds a 149-line server method, `importLibraries.js`. It pre-generates IDs, remaps `parentId`, `ancestors` and `referenceNodeId`, and calls `rebuildNestedSets`. The browser-side half that fetches libraries from dicecloud.com over DDP sits in a gitignored folder and was never published ([ardunaline compare](https://api.github.com/repos/ThaumRystra/DiceCloud/compare/develop...ardunaline:develop)). JPugetGil's in-app export and import is the better design, because it keeps IDs and offers replace semantics, but it is written against Meteor 3's async APIs. The fork's own creature-archive code maps almost directly onto libraries, and the tree helpers (`renewDocIds`, `setLineageOfDocs`, `rebuildNestedSets`) already exist (local: `imports/api/library/methods/copyLibraryNodeTo.js`). The risks are references between nodes that ID renewal may break, the lack of a library migration function for old exports, SRD-sized libraries exceeding DDP message limits, and the need to rewrite `owner` and `root` on the server. Nobody checked whether library authors' licences or dicecloud.com's terms allow copying public libraries. The cheapest onboarding win needs no new code: keep `disallowCreatureApiImport` off so players can pull existing characters from dicecloud.com through the existing `importCharacterFromDiceCloudInstance` method, after checking that it still works against today's upstream API.

**Change 8, patching dependencies**, is only partly possible on Node 14. Running `npm audit` against production dependencies reports **40 vulnerabilities, 8 of them critical** (local audit, 20 October 2026). The deprecated `request` package carries an SSRF flaw ([GHSA-p8p7-x288-28g6](https://github.com/advisories/GHSA-p8p7-x288-28g6)) and drags in vulnerable `form-data`, `qs` and `tough-cookie`, and it has no fix at all. `dompurify` 2.x has XSS issues that matter because the app renders user markdown. Vuetify 2 has a high-severity prototype-pollution advisory ([GHSA-3jp5-5f8r-q2wg](https://github.com/advisories/GHSA-3jp5-5f8r-q2wg)) whose fix needs a major version. Replacing `request` and bumping `dompurify`, `lodash`, `ws` and the AWS SDK are achievable on 2.16. The fixes for `bcrypt` 6, `sharp` 0.35, Vue and Vuetify all need major upgrades, and newer versions may refuse Node 14 (unverified). The honest verdict is to fix what you can, accept that the rest is blocked until the platform moves, and keep the attack surface small with changes 6 and 7. Change 12, auto-archiving (#390) and i18n (#395, 131 files), adds little for 5–10 players and is built on Vue 2 code that Meteor 3 will replace. Change 13, adding Redis, a CDN or APM, adds failure modes with no benefit at this scale.

## Meteor 3 is a re-port, and Oracle's terms are still unclear

**Change 15, the platform migration**, is the only change that fixes the root cause. Meteor 2.x entered maintenance mode in July 2025 and "will completely reach End-of-Life in December 2025" ([Meteor forums](https://forums.meteor.com/t/meteor-supported-versions-clarification-transition-timeline/63646)). Meteor's extended Node 14 patches ended in April 2024 ([Meteor blog](https://blog.meteor.com/announcing-extended-support-maintenance-for-node-js-14-f9e8381f8bb5)). Meteor 3.5 runs Node 24, supported to April 2028 ([Node release schedule](https://raw.githubusercontent.com/nodejs/Release/main/schedule.json)), with native Linux ARM. The cost is two migrations bound together. First, Meteor 3 removes Fibers. The codebase has about 440 synchronous Mongo call lines, 97 ValidatedMethods and 30 publications against roughly 54 existing `*Async` calls (local grep). Second, the Vue 2 compiler package, `akryum:vue-component`, has no Meteor 3 release, and its author moved to Vite ([Meteor forums](https://forums.meteor.com/t/meteor-3-update-conflicting-instructions-and-conflict-errors/62263)). So Meteor 3 also forces Vue 3 and Vuetify 3 across 352 `.vue` files, 121 of which use the `meteor: {}` reactive block. The research team's estimate is 4–10 weeks of server-side async work plus 2–4 months of frontend porting. Those are inferences, not measured data.

Two reference implementations exist, and neither can be merged. Upstream's DC-16 branch begins with a commit titled "Machine translation to Meteor 3, vue 3 composition, vuetify 3" touching 496 files, has been idle since 10 May 2026, and still uses the 5e tri-state advantage that RA replaced ([DC-16 commits](https://github.com/ThaumRystra/DiceCloud/commits/DC-16-migrate-to-meteor-3)). It edits 12 fork-modified files and renames two others from `.js` to `.ts`. JPugetGil's fork is further along, on Meteor 3.5.2, Vue 3, Vuetify 4 and Node 24 with CI, but it has reorganised the whole tree and adds 5e engine features that would collide with RA. The lowest-risk sequence starts on 2.16. Convert server code to the `*Async` APIs, which 2.16 already supports (the fork even has `zodern:fix-async-stubs` installed). Replace the Fibers-era packages: `peerlibrary:reactive-publish` has an async-aware successor, `nachocodoner:reactive-publish` ([Meteor forums](https://forums.meteor.com/t/reactive-publish-for-meteor-3-revived-and-ready-for-composite-data-publishing/63818)), and `simple:rest` and `mikowals:batch-insert` would need rewrites. Only then port the UI and re-apply the RA files to the new structure, using DC-16 as a map. The verdict is high long-term value, very high RA conflict, and not before launch.

**Change 14, upgrading to Oracle Pay-As-You-Go**, is an account setting with outsized impact. Oracle reclaims Always Free instances when, over seven days, 95th-percentile CPU, network and (on A1) memory are all below 20% ([Oracle Always Free Resources](https://docs.oracle.com/en-us/iaas/Content/FreeTier/resourceref.htm)). A tabletop server for a few friends looks idle most weeks. Community sources say PAYG accounts are exempt and that Always Free resources stay free after upgrading ([51sec blog](https://blog.51sec.org/2023/02/oracle-cloud-cleaning-up-idle-compute.html)), but Oracle's documentation does not confirm the exemption. If you upgrade, set a $1 budget alert. If you don't, keeping memory use legitimately above 20%, for example with a larger WiredTiger cache, is a better defence than synthetic CPU burners, which go against the spirit of the terms. Either way, change 5's off-Oracle backups are mandatory.

### What remains unverified

Several load-bearing facts could not be confirmed, and each should be checked before you rely on it. **Meteor 2.16 on Linux arm64** has no official support, and no source reports a 2.16 server bundle running on any arm64 Linux host. **fibers@5 on arm64 Node 14** is untested: it needs a native compile with python3, make and g++ in the image. It is also unknown whether Meteor's patched Node 14.21.4 ships an arm64 binary, so upstream Node 14.21.3 may be the only option. **Oracle's A1 allowance** conflicts between sources. The page fetched on 20 October 2026 states 1,500 OCPU-hours and 9,000 GB-hours a month, equivalent to **2 OCPUs and 12 GB**, while the long-cited figure is **4 OCPUs and 24 GB**. Check your console's Limits page; either is ample for this workload. **The PAYG reclamation exemption** rests on community reports only. Other open items: MongoDB 8 behaviour with driver 4.17 (including oplog tailing); the MongoDB 8 kernel bug SERVER-121912, which comes only from a comment in JPugetGil's compose file; whether the bundle's relative `assets/app` path resolves where expected; OCI S3 signing with the hardcoded `ENAM` region; whether `nachocodoner:reactive-publish` supports Meteor 2.16; the Meteor 3 status of `ostrio:files`, `percolate:migrations`, `littledata:synced-cron`, `bozhao:link-accounts` and the aldeed packages; whether JPugetGil's security fixes describe bugs present in 2.16; and whether newer patched dependency versions still run on Node 14.

## Conclusion

Do the work in four phases. **Phase 0 (before the move, about a week):** changes 1–4, ending with the ARM proof of concept on the actual A1 instance. Build the fork's bundle in x86 CI, rebuild the native modules on arm64, boot it against MongoDB 7.0, and roll a 2d10 attack. That test is the gate for the whole plan. **Phase 1 (launch):** changes 5–7 and the PAYG decision, so the instance is backed up, behind HTTPS, invite-only and sending correct links before any player logs in. **Phase 2 (first month):** the dice-seed audit, library import/export, `request` and `dompurify` replacement, and the safe cherry-picks (#403, DC-6, and #400 after its RNG check). **Phase 3 (ongoing):** async conversion on 2.16 in small shippable steps, then the Meteor 3 and Vue 3 re-port. If the ARM test fails, Phase 3 jumps to the front, because native Linux ARM is the one thing Meteor 3 brings that no amount of Dockerfile cleverness can supply on 2.16.

The less obvious lesson is that the fork's biggest liability is not its age but its isolation. Upstream merges almost nothing, its Meteor 3 branch has stalled, and the one active derivative is drifting into its own codebase, so no future upstream merge will carry Reverent Abyss forward for free. That makes the fork's discipline of keeping RA logic in separate files and covering it with tests the asset that most reduces the cost of every later change, and it argues for writing the dice-path tests before touching the roll-security fix or any part of the migration.
